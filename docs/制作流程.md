# 制作流程

这个工程将“要演什么”和“怎样计算画面”分开：分镜约束故事，帧表约束时间，角色图提供表演材料，Blender 和二维合成器负责落实镜头。下面记录的是正式全片路径，早期 demo 的命令另列在最后。

## 环境与输入

原制作环境：Windows、Python 3.12.10、Blender 5.2、FFmpeg，成片为 1920×1080、30 fps。`requirements.txt` 记录当时实际安装的主要 Python 包；它不是含全部传递依赖的锁文件，也没有承诺跨平台开箱即用。

```powershell
py -3.12 -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python src\tools\fetch_fonts.py
.venv\Scripts\python src\tools\fetch_fonts.py --check
```

Blender 的 `bpy`、`bmesh` 和 `mathutils` 由 Blender 自身提供，不安装进普通 Python。FFmpeg 要在 PATH 中。三维渲染入口依次使用 `BLENDER_EXE` 环境变量、PATH 中的 `blender`，最后尝试原作者的 Windows 安装路径：

```powershell
$env:BLENDER_EXE = 'C:\Program Files\Blender Foundation\Blender 5.2\blender.exe'
```

| 自备文件 | 内容与约束 |
|---|---|
| `input/song.mp4` | 含原曲音轨的媒体文件；扩展名及路径在拼接代码中固定使用 |
| `input/lyrics.ass` | 与同一版音频对应、包含卡拉 OK `\k` 音节标记的罗马音 ASS 时间轴 |
| `work/analysis/lyrics_ja.txt` | 对应版本的日文歌词文本，供字符与音节对齐；不能拿另一版翻唱或歌词替代 |

**只有歌曲音频还不够。** `src/analysis/lyric_timing.py` 并非语音识别器：它读取 ASS 的演唱时间，把罗马音和日文读音做序列对应。仓库不分发这两份完整歌词／卡拉 OK 文件。`fetch_lyrics.py` 是当时的调研辅助脚本，在线结果可能改变，不应作为正式输入的唯一来源。

准备数据目录，并使用随仓库提供的数值节拍网格：

```powershell
New-Item -ItemType Directory -Force work\analysis | Out-Null
Copy-Item data\audio.json work\analysis\audio.json
.venv\Scripts\python src\analysis\lyric_timing.py
```

结果为 `work/analysis/lyrics_timed.json`，其中含歌词文本，因此不进入 Git。检查输出的未匹配字符和 `UNCLAIMED`，再按声音核对句首、重复字、长音和句尾。代码中的歌词行号与原制作输入绑定；自己准备的轴即使“能对齐”，行数或分句不同仍可能让镜头引用错行，需要相应调整。

若研究节拍分析本身，可从音频重新计算：

```powershell
ffmpeg -i input\song.mp4 -vn -ac 1 -ar 22050 work\analysis\song.wav
.venv\Scripts\python src\analysis\analyze_audio.py
.venv\Scripts\python src\analysis\beat_grid.py
```

上述两步会更新本地 `audio.json`。原片的数值基准保存在 `data/audio.json`；不要把未经听校的新分析结果直接当作它的等价替代。

## 先预览一张，再渲染一段

二维预览不需要启动 Blender，也不需要重新生图：

```powershell
.venv\Scripts\python src\tools\preview.py c1 Opening 8
.venv\Scripts\python src\tools\preview.py s03 Digging 55 62
.venv\Scripts\python src\tools\preview.py c6 OpenEye 197 201 204
```

`preview.py` 的参数是模块名、类名、**歌曲全局秒数**，不是该段从零起算的时间。输出在 `work/qc/<clip.name>/` 和 `work/qc/<clip.name>_sheet.jpg`。同名预览会更新本地同名图片。

3D 段落的二维叠加层会读取已经生成的 PNG；不能把 `preview.py` 当成自动渲染整个三维场景的入口。先生成对应的 3D 组，再预览叠加层。

## 三维镜头：几何与画风分开

每组镜头通常有三份相互对应的代码：

| 文件 | 职责 |
|---|---|
| `src/three/shared_<shot>.py` | 歌曲时段、镜头参数、相机与对象的共享约定 |
| `src/three/shot_<shot>.py` | 在 Blender 中搭场景并输出 EXR 数据通道及编号表 |
| `src/npr/paint_<shot>.py` | 读取通道，计算平涂、硬边阴影、墨线和图层 |

正式使用 9 组：`c2`、`c3`、`c4`、`gate`、`lockers`、`train`、`room`、`room2`、`outro`。例如：

```powershell
.venv\Scripts\python src\three\pipeline.py gate
```

已完成的上色帧在 `work/render/gate_png/`。流水线会跳过已完成帧；有意重做某个范围时，先阅读 `pipeline.py` 中 `--redo-from` 的行为，它会替换该范围的旧输出。

保留 EXR 后，只改画风可用重上色：

```powershell
$env:SHOT_KEEP_EXR = '1'
.venv\Scripts\python src\three\pipeline.py gate
.venv\Scripts\python src\three\repaint.py gate
```

`KIT_GPU=1` 控制 Blender CUDA，`PAINT_GPU=1` 控制 Python 上色中的 GPU 路径；后者需要另行安装匹配显卡和驱动的 PyTorch。`N_BLENDER`、`N_PAINTER` 控制并行度。原环境使用 RTX 4060 Laptop；这些参数需要按自己的机器测量，不代表相同并行度适用于所有显卡。

完整通道缓存曾达到百 GB 级，审片图和版本备份另占空间。仅研究方法或修改二维镜头，不需要下载或生成全部中间缓存。

## 正式全片入口

**正式入口是 `make_full.py` 与 `assemble_full.py`。** `make_full.py` 会启用 Blender GPU，默认尝试 GPU 上色，保留 EXR；确认输入和环境后再运行：

```powershell
.venv\Scripts\python src\make_full.py
```

它按顺序调用 3D 组，检查缺帧，再渲染各段、拼接全片。断点标记为 `work/full/redo_done.txt`；现有段落保存在 `work/full/<name>.mp4`。

只检查段落是否齐全：

```powershell
.venv\Scripts\python src\assemble_full.py check
```

只重新渲染指定段落，再拼接：

```powershell
.venv\Scripts\python src\assemble_full.py render s12
.venv\Scripts\python src\assemble_full.py build
```

`render s12` 会重做指定段；不带段名的 `render` 跳过已存在的段落。**三维画面改动后，既要重做 3D 组，也要重做引用它的二维段落**，否则拼接仍可能使用旧段落视频。

| 渲染段 | 歌曲时间约 | 模块／类 |
|---|---|---|
| `s00`、`s01b` | 0:00–0:22.70 | `c1.Opening`、`s01b.MediaMachine` |
| `s02a`–`s02d` | 0:22.70–0:52.20 | 校门、鞋柜、电车、草稿 |
| `s03`、`s04a` | 0:52.20–1:09.30 | `s03.Digging`、`s04a.PaperFall` |
| `s04`、`s05` | 1:09.30–1:36 | `c2.Samui`、`c3.Tooi` |
| `s06` | 1:36–1:43.87 | `s06.Ranking` |
| `s07`、`s07x` | 1:43.87–2:12.97 | `c4.Rin14`、`s07x.Stickers` |
| `s08`、`s09` | 2:12.97–2:44.33 | `s08.Fast`、`c5.Hate` |
| `s10`、`s11a`、`s11b` | 2:44.33–3:13.93 | `s10.Room`、`s11a.Room2`、`s11b.Wall` |
| `s12` | 3:13.93–3:26 | `c6.OpenEye` |

精确边界由 `assemble_full.py` 的 `TABLE` 决定，采用左闭右开帧区间，不能从表格四舍五入后的秒数反推帧数。

拼接输出为 `out/少女A_full.mp4`。**`out/少女A_正式版.mp4` 是当时单独压缩的交付文件名，不是 `make_full.py` 的直接输出。**

## 旧脚本为什么还在

- `make_all.py`、`assemble.py`、`finish_v3.py`、`finish_v5.py` 属于 demo／阶段性流程；文件名里的版本不是正式全片入口的版本号。
- `work/gen/` 是提示词库与原素材处理记录，供理解角色制作；不是每份历史生成任务都需要重跑。
- `work/eye/key6/` 是结尾生成与对齐过程的选录，仍保留当时的输入路径。部分候选原图未分发，因此这些历史构建脚本不保证可以直接执行；正式渲染用到的结果已在 `assets/gen/end/`。
- `C6_EYE` 的旧候选选项指向本地实验文件，默认定稿图已随仓库放到 `assets/gen/eyes/`。不要把“源码里仍有选项”理解成全部候选图都已公开。

阅读过程资料和重跑成片是两种不同的需求；前者可以直接使用仓库，后者还需要配齐歌曲及对齐数据，并按机器条件验证渲染。
